# Self-Review 追加ルール（CrabShell プロジェクト）

このファイルは `/self-review` スキルが起動するレビューサブエージェントに追加で渡されるプロジェクト固有のルール集。レビュー観点として遵守すること。

## 調査方針

### デコンパイル / 逆アセンブルは最終手段

ライブラリの内部実装・例外型・挙動を調べる際、**まず Web 検索で対応すること**。

調査の優先順位:

1. 公式ドキュメント・API リファレンスを Web 検索
2. GitHub リポジトリのソースコードを Web で確認
3. 上記で解決しない場合のみ、最終手段としてデコンパイル / 逆アセンブル / Gradle キャッシュ探索

**Why:** デコンパイル・逆アセンブルは重く侵襲的で、多くの場合ドキュメントや公式リソースで十分な情報が得られるため。

**レビュー時の適用:** PR の調査過程・実装根拠が「デコンパイル結果」に依存しており、かつ公式ドキュメントで同じ情報が得られる場合は指摘する。

## レビュー対象外の項目

### PR 説明文の Test plan のチェック状況・表現は指摘しない

PR 本文の Test plan セクション（チェックリストの未チェック / past tense / 実機確認済みかどうか等）は **レビューで指摘しないこと**。

**Why:** 手動テスト項目のチェック状況は実装そのものの品質と独立しており、コード review の関心事ではない。CrabShell ではこの類の指摘は user 判断保留に常に振り分けられるため、毎回挙げると保留リストが膨らむだけで生産性が下がる。

**適用範囲:** 「Test plan を past tense にすべき」「チェック済みにすべき」「ユニットテストがない旨を補足せよ」等の Test plan 文面に関する指摘全般。コード変更が壊している既存テストの指摘や、テスト追加の必要性そのものの議論は引き続き対象。
